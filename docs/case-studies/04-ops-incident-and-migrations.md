# 4. 운영 사고에서 마이그레이션 구조로

## 문제

원본은 번호가 붙은 SQL 파일 25개(약 1.6만 줄, 그중 스키마 파일 하나가 약 4천 줄)를 SQL Editor에 순서대로 붙여 넣어 설치하는 구조였다. 운영을 시작한 뒤에는 이 파일들을 다시 통째로 실행할 수 없었다. 그래서 고칠 함수의 몸통을 복사해 날짜가 붙은 패치 파일로 실행했다.

**2026-09-18 사고**

초기 커밋 시절의 스키마 파일이 라이브 DB에서 통째로 실행됐다.
- 운영 중인 함수 3개가 옛 몸통으로 덮였다.
- RLS 정책 2개가 `using (true)`로 풀렸다.

증상은 서로 달라 보였다. 관리자 화면에 들어갈 수 없었고, 숨김 계정이 목록에 보였고, 이겨도 배당이 적었고, 일부 아이템 효과가 사라졌고, 응답이 느려졌다. 그런데 원인은 모두 같았다.

## 결정

**사고 당일**
- 증상과 원인을 1:1로 대응한 표를 만들었다.
- 망가진 함수와 정책만 정본에서 복사해 되돌리는 복구 스크립트를 실행했다.
- 아이템 카탈로그, 원장, 코인 데이터는 사고에 영향을 받지 않았으므로 건드리지 않았다. 스키마 파일 전체를 다시 실행하면 낡은 아이템 데이터가 최신 카탈로그를 덮어쓰기 때문이다.

**사고 이후 규칙: "함수 몸통은 한 파일에만 둔다"**
- 패치 파일에 사본을 둘 수밖에 없는 경우에는, 그 파일이 낡는 순간 머리에 "돌리지 말 것"을 적었다.
- 하지만 이 규칙은 사람의 주의력에 기대는 방식이었다. 7주 동안 60건을 패치하면서 같은 실수가 날 뻔한 경우가 여러 번 있었다. 자세한 내용은 [ops-log](../ops-log.md)에 있다.

**공개판에서 바꾼 것**
- **Supabase CLI 마이그레이션.** [`supabase/migrations/`](../../supabase/migrations)에 도메인별 파일 11개를 날짜순으로 둔다(core, items, games, trade, arena, social, admin, race, rules, platform, guest). `supabase db reset` 한 줄로 빈 DB에서 전체를 재현한다.
- **각 파일 머리에 규칙을 적었다.** "여기 정의된 함수의 몸통은 저장소 전체에서 이 파일에만 있다." 이미 배포한 마이그레이션은 고치지 않고, 변경은 새 파일로만 추가한다.
- **규칙 상수를 한 곳으로 모았다.** 원본은 같은 값을 SQL 상수 파일과 클라이언트 `game.ts`에 따로 적어 두었다. 지금은 `get_rules()` 한 곳에서 내려준다. 클라이언트 테스트용 픽스처도 `node scripts/fixtures.mjs`가 서버에서 다시 뽑는다. `--check`를 붙이면 서버와 픽스처가 어긋났는지만 검사한다.
- **CI.** PR마다 lint, typecheck, build, 금지어 검사, Vitest, `supabase test db`(pgTAP)를 돌린다.

## 결과

- 설치 과정이 "SQL 25개 붙여넣기"에서 `supabase start`와 `supabase db reset` 두 줄로 줄었다.
- 함수가 덮이는 사고는 구조적으로 일어나기 어려워졌다. 함수 정의는 마이그레이션 이력에 한 번만 나오고, DB를 초기화하면 항상 최신 정의로 재현된다.

## 한계와 다음에 한다면

- 처음부터 마이그레이션 도구를 썼다면 사고 자체가 없었을 것이다. 원본을 빠르게 만드느라 SQL을 한 파일에 계속 키운 것이 원인이었다. 다음 프로젝트에서는 첫날부터 마이그레이션과 테스트 DB를 둔다.
- 데모 DB에는 아직 운영 데이터가 없어서, 데이터를 보존하면서 스키마를 바꾸는 마이그레이션은 검증하지 못했다.
