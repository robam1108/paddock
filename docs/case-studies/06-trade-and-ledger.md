# 6. 개인 거래와 원장

## 문제

플레이어끼리 코인과 아이템을 주고받는 개인 거래를 만들었다. 한쪽이 제안하고 상대가 수락하거나 역제안하는 방식이다. 이때 막아야 할 것은 세 가지였다.

- **이중 지출**: 같은 50코인으로 두 사람에게 동시에 선물을 보내 두 건 모두 성사시키는 것.
- **교착 상태**: A→B 거래와 B→A 거래가 동시에 성사될 때 서로의 행을 기다리며 멈추는 것.
- **추적 불가**: 코인이 어디서 왔는지 설명할 수 없게 되는 것. 운영자도 플레이어도 설명할 수 있어야 한다.

## 결정

코드는 [`supabase/migrations/20261111000400_trade.sql`](../../supabase/migrations/20261111000400_trade.sql)에 있다.

**제안 단계에서는 코인을 묶지 않는다**
- 제안할 때 잔액을 예약하지 않는다. 그래서 같은 50코인으로 제안 여러 건을 보낼 수 있다.
- 대신 **성사 순간에 다시 확인한다**. 이렇게 하면 예약을 풀어 주는 로직이 필요 없어 상태가 단순해진다.

**성사는 한 함수에서 잠그고 다시 확인한다**
- `app.exec_trade`는 다음 순서로 처리한다.
  1. 거래 행을 `for update`로 잠근다.
  2. 두 사람의 `profiles` 행을 **항상 id 순으로** `for update` 잠근다. 잠그는 순서가 늘 같으므로 교착 상태가 생기지 않는다.
  3. 잠근 상태에서 양쪽의 잔액과 아이템 보유량을 다시 확인한다. 모자라면 `PARTNER_SHORT_COINS`, `NOT_ENOUGH_ITEMS` 같은 오류를 던진다.
  4. 코인과 아이템을 옮기고, 양쪽 원장에 한 줄씩 남긴다.

**원장(ledger)**
- 코인이 움직이는 모든 경로가 `app.log`로 기록을 남긴다. 게임, 거래, 관리자 지급과 회수가 모두 여기에 해당한다.
- 각 줄에는 `coin_delta`와 `coin_after`가 있어서, 한 사람의 잔액 변화를 처음부터 이어 볼 수 있다.
- 거래로 남긴 원장 줄에는 `trade_id`가 있다.
- 플레이어는 자기 원장을 프로필 화면에서 읽을 수 있다(RLS SELECT, `user_id = auth.uid()`).

**운영 중 추가한 관리 기능**
- 관리자 거래 취소 `panel_revert_trade`는 양쪽이 그 거래로 **받은** 것을 각자에게서 거둔다. 이미 써 버렸거나 남에게 넘긴 몫은 쫓아가지 않고, 지금 가진 만큼만, 코인은 잔액 한도까지만 거둔다. 실제로 거둔 양은 `reverted_detail`에 기록한다.
- 이 설계에는 "음수 잔액을 만들지 않는다"는 불변식과 "회수 기록은 실제와 일치해야 한다"는 요구가 함께 반영돼 있다.
- 플레이어를 삭제해도 거래 기록은 남는다. 외래 키는 `on delete set null`이고 이름은 별도 컬럼에 남긴다.

## 결과

[`supabase/tests/03_security.sql`](../../supabase/tests/03_security.sql)의 "거래 이중 지출" 블록이 다음을 검증한다.
- 50코인만 가진 사용자가 50코인짜리 선물 두 건을 걸고 상대가 둘 다 수락하면, 두 번째는 실패한다.
- 잔액은 0에서 멈춘다.

## 한계와 다음에 한다면

- 제안 단계에서 코인을 묶지 않으므로, 상대는 수락 버튼을 누른 뒤에야 거래가 불가능하다는 것을 알게 된다. 이용자가 30명 남짓이라 이 방식을 택했다. 거래량이 많아지면 제안할 때 금액을 예약하는 방식으로 바꾸고 만료 처리를 두는 편이 사용자 경험이 낫다.
- 원장은 감사(audit) 용도일 뿐이고, 잔액의 정본은 `profiles.coins`다. 둘이 어긋났는지 주기적으로 대조하는 검증 작업은 아직 없다.
